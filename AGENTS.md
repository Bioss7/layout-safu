# layout-safu — обязательные правила

- Работай как опытный фронтенд-разработчик: проверяй каскад, адаптивность, фактические размеры и отступы в браузере и соответствие Figma. Предпочитай плоские БЭМ-селекторы; применяй calc() только для необходимых расчётов геометрии. В SCSS не оставляй комментарии: замечания и пояснения храни в документации и реестрах.
- Различия похожих элементов страницы оформляй явными БЭМ-модификаторами на самих элементах, например `.tabs__tab--faq`. Для оформления варианта используй один класс в селекторе вместо контекстных и составных селекторов вроде `.faq .tabs__tab` или `.tabs.tabs--line`. Базовый класс и модификатор сохраняй вместе в HTML. Все стили компонента, его вариантов, состояний и адаптивов храни в одном SCSS-файле компонента; не распределяй переопределения по файлам соседних блоков. Для каждого брейкпоинта объединяй правила и удаляй дубли.
- Для работы с SCSS также используй [scss-best-practices](.agents/skills/scss-best-practices/SKILL.md); для реализации макета через MCP — [figma-implement-design](.agents/skills/figma-implement-design/SKILL.md) вместе с figma-design-to-code. Правила проекта и прямые указания пользователя имеют приоритет.
- Перед работой кратко сообщить план и выбрать нужные инструкции ниже. Не загружать все документы без необходимости.
- Каждая страница имеет собственные SCSS, JS, изображения и шрифты. Готовые блоки копируются; исходная страница не меняется.
- Flexbox вместо Grid. Обязательная семантическая HTML-вёрстка и БЭМ; тег выбирать по назначению элемента. Не придумывать отсутствующие макеты, состояния и неоднозначное поведение.
- Основные брейкпоинты: 390, 576, 768, 992, 1150, 1200, 1440px; остальные существующие точки отдельных страниц сохраняются. Между ними — резиновая вёрстка. Все адаптивы оформлять только через `@include breakpoint($bp-992)` с ровно одной именованной переменной `$bp-*` из `_vars.scss`, имя которой соответствует значению в пикселях. Для каждой точки — свой блок внизу файла компонента, от большего к меньшему; повторные блоки одной точки объединять. Диапазоны, второй аргумент, `null`, числовые границы, `screen-*` и собственные media-диапазоны в компонентах запрещены. Стили выше наибольшей точки задавать в базовых правилах. Новые точки добавлять только с явного согласия пользователя; точка 900px исключена. Существенное перестроение блока на существующей точке также пояснить.
- CSS-функции clamp(), min() и max() в SCSS запрещены. Для геометрии использовать явные округлённые размеры, проценты, понятные calc() и Flexbox. Не интерполировать font-size, line-height и letter-spacing через calc(): значения типографики задавать явно на брейкпоинтах.
- Стили должны читаться человеком: непрозрачные цвета — HEX, rgb()/rgba() — только когда нужна прозрачность; значения цветов брать из токенов. Дробные пиксельные размеры Figma округлять до целых (1098.551px → 1099px), сохраняя исходные измерения в кэше. Пропорции ресурсов и переносы текста проверять визуально; округление не заменять сложными формулами ради субпиксельного совпадения. Подробности — в scss-architecture.
- Если необходимый цвет не определён макетом, требованиями или готовым компонентом, использовать var(---Accent-Accent-100, #00AEEF). Наследование и намеренная прозрачность не считаются отсутствующим цветом.
- Сначала требования, реестр компонентов, локальный код и кэш Figma. Типографику, иконки и неочевидную функциональность не придумывать; существенную оставшуюся неоднозначность уточнять у пользователя. О найденных отличиях от макета сообщать в чате с указанием блока.
- При вёрстке новых страниц и адаптивных экранов не изменять шапку и подвал без прямого указания пользователя. Изменения общих стилей не должны влиять на их оформление и поведение.
- Обязательно сверять внутренние отступы, расстояния между элементами и секциями с макетом; учитывать суммирование padding, margin и gap, проверять фактическую геометрию в браузере и накопленный вертикальный сдвиг.
- Сначала использовать локальный кэш Figma; обращаться к MCP только за недостающими или подтверждённо устаревшими данными. Полученные контексты, скриншоты и точные измерения сохранять в кэш страницы с индексом источников и датой.
- Перед выгрузкой составить короткий перечень нужных узлов и параметров: что уже подтверждено в кэше, что отсутствует и что устарело. Не запрашивать дерево всей страницы и контексты всех брейкпоинтов, когда достаточно конкретных секций или инстансов; большие файлы и ответы читать выборочно.
- При работе с субагентами основной агент отвечает за сверку кэша с текущим файлом Figma, получение точных значений через Dev Mode и запись измерений с file key, node ID, брейкпоинтом и датой. Исполнителям передавать соответствующие файлы кэша; они берут размеры блоков, padding, margin, gap, параметры типографики и геометрию иконок только из подтверждённых данных. Если измерения нет или источники противоречат друг другу, субагент сообщает основному агенту конкретный узел и недостающий параметр, не назначая значение на глаз.
- Для каждой изменённой секции сверять рассчитанные в браузере размеры и положение элементов, padding, margin, gap, типографику и накопленный вертикальный сдвиг с кадром того же брейкпоинта. Для SVG проверять и CSS-размер контейнера, и фактическую геометрию рисунка.
- При сверке макета проверять каждый видимый блок и его дочерние элементы отдельно: ширину, высоту, координаты, padding, margin и gap по Figma и computed styles браузера. Совпадение общего размера или положения секции не заменяет проверку её внутренних элементов; результат фиксировать по блокам с node ID источника.
- Отличать прямое свойство узла Figma от вычисленной корректировки HTML-обёртки. Если обёртки нет в макете, фиксировать исходные координаты и размеры дочерних узлов, формулу корректировки и итоговые computed styles; не называть вычисленное значение отступом из Figma.
- Без явного разрешения пользователя не менять PHP, сервер и другие страницы за пределами текущей задачи; не выполнять импорт ресурсов в Битрикс и деплой. Без явного разрешения не выполнять git add/commit/push.
- Не исследовать node_modules/ и dist/. Большие исходники читать точечно. Проверка: pnpm build и браузерный preview, не бесконечный pnpm dev.
- Сгруппировать подтверждённые правки и затем выполнить одну сборку и одну серию браузерных проверок по нужным ширинам. Повторять их только после новых изменений, ошибки или конкретного непроверенного расхождения.
