# layout-safu — правила вёрстки

## Границы и порядок работы

- layout-safu/ — самостоятельный Git-репозиторий. Все исходники HTML, SCSS, JavaScript, адаптивы, ресурсы, инструменты и документацию вёрстки вести внутри него; описание проекта и команд — в [README.md](README.md).
- При работе в составе safu-dev-bus проверять состояние и diff обоих репозиториев отдельно: из корня — git status и git diff, для вёрстки — git -C layout-safu status и git -C layout-safu diff. Коммит родительского проекта не сохраняет изменения файлов вёрстки. Не менять устройство Git и не выполнять git add/commit/push без прямого запроса.
- Соблюдать [корневые правила и роли](../AGENTS.md). Здесь уточняются требования к вёрстке; разрешения на PHP, сервер, импорт, Git и деплой не расширяются.
- Перед работой кратко обозначить задачу и выбрать инструкции из таблицы. Не загружать все навыки и большие файлы без необходимости; node_modules/ и dist/ не исследовать как исходники.
- Менять только назначенную страницу и её ресурсы. Страницы независимы: готовый блок копировать и адаптировать в новой странице, исходную не менять.
- Шапку и подвал не менять без прямого указания пользователя, в том числе через общие стили. Старые страницы целиком не рефакторить вне задачи.
- Семантический HTML, БЭМ, Flexbox и Vanilla JavaScript. Компонентные стили, состояния и адаптивы хранить вместе; детали — в профильных навыках.
- Сначала проверить требования, реестр компонентов, локальный код, ресурсы и кэш Figma. Не придумывать отсутствующие макеты, иконки, типографику и существенное поведение. Оставшуюся существенную неоднозначность уточнить.
- Не изменять документ Figma без указания пользователя. При реализации по Figma применять доступный навык `figma-design-to-code` вместе с проектным `figma-mcp`.
- Координатор либо назначенный аналитик Figma готовит подтверждённые данные и передаёт исполнителям ссылки на кэш. При нехватке данных исполнитель сообщает узел и параметр, не подбирает значение на глаз.
- До исправления каждого блока получить и сохранить полный необходимый контекст Figma для блока и значимых дочерних элементов. Общий скриншот и сокращённое дерево страницы не заменяют измерения; усечённый ответ уточнять запросами дочерних узлов. Порядок: кэш → недостающие подробные данные → измерения → исправления → скриншоты страницы и блоков → повторная сверка. Подробности — в `figma-mcp` и `interface-review` ниже.
- Проверки выбирать по изменению. Для правок интерфейса сгруппировать изменения, выполнить сборку внутри layout-safu и серию браузерных проверок; повторять после новых правок, ошибки или конкретного непроверенного расхождения. Для изменений только документации сборка не нужна.
