# SCSS страницы

Блоки подключаются через @use. В начале: @use "../_mixins" as *; и @use "../_vars" as *;. Токены — своей страницы. Общие элементы — common.scss, типографика — typography.scss. Без дубликатов и неиспользуемых правил.

- Элементы — плоские .block__element. Вложенность только для модификаторов, псевдоклассов/элементов и media. Один базовый селектор в файле.
- Flexbox без grid-*. Между 1920 и 390px — гибкие ширины, flex-basis, проценты и простые calc() для геометрии, например calc(100% - 40px). CSS-функции clamp(), min() и max() в SCSS запрещены. Не интерполировать font-size, line-height и letter-spacing через calc(), vw или цепочки переменных: типографику задавать явными значениями на именованных брейкпоинтах. Высоту текстовых блоков не фиксировать.
- Основные брейкпоинты через переменные/миксин: $bp-390:390px, $bp-576:576px, $bp-768:768px, $bp-900:900px, $bp-992:992px, $bp-1150:1150px, $bp-1200:1200px, $bp-1440:1440px. Адаптивные правила собирать отдельными именованными блоками внизу файла компонента, от большего к меньшему, с плоскими БЭМ-селекторами внутри. Обычные max-width оформлять через @include breakpoint($bp-...). В компонентах не писать пары min-width/max-width, собственные диапазоны или арифметику границ.
- Если существующие версии 576/768/390 нужно изолировать, чтобы сохранить младший макет без множества сбрасывающих переопределений, допустимы именованные @include screen-576 и @include screen-768. Их диапазоны определять только централизованно в _mixins.scss через современный CSS range syntax без смещений +1px: например ($bp-390 < width <= $bp-576) и ($bp-576 < width <= $bp-768). Компонент знает только имя адаптива; версия 390 сохраняется отдельным breakpoint($bp-390). Не дублировать определения диапазонов по компонентам.
- Между точками — резиновая вёрстка. Не вводить дополнительную точку, пока композицию можно исправить гибкими размерами в этом наборе. Если дополнительная точка необходима, до изменения сообщить ширину, блок и причину. Существенное перестроение блока на существующей точке также пояснять. Проверять промежуточные ширины и обе стороны границы брейкпоинта; это проверка, а не основание для арифметики границ в SCSS.
- Секции: явные padding-top и padding-bottom с понятными значениями на основных брейкпоинтах, не внешний margin и не скрытое деление общего --section-gap. Расстояния соседей не удваивать. Учитывать собственную заливку секции: общий фон страницы не должен просвечивать через подтверждённый непрозрачный фон.
- Background-color/image/position/size/repeat отдельно, без background shorthand. Так же разделять mask и -webkit-mask.
- Одноцветные стрелки/иконки — маска с background-color:currentColor; проверять цвет вместе с родителем, включая белый на тёмной карточке.

## Состояния

Проверять применимые hover, active, focus-visible, disabled, readonly, filled/placeholder-shown, invalid, autofill, checked, selected, expanded. Неприменимые состояния не добавлять. Псевдоклассы дополняются БЭМ-модификаторами и aria-*.

Эффекты — из макета или прямого указания. Не придумывать поворот, прозрачность, масштабирование. Если необходимый цвет не определён макетом, требованиями или готовым компонентом, использовать var(---Accent-Accent-100, #00AEEF). Это общий запасной цвет, а не найденный стиль макета. Намеренное наследование цвета и прозрачность не считать отсутствующим оформлением; фон или рамку без необходимости не окрашивать. Для отсутствующего hover использовать этот акцентный цвет текста/маски и сохранять доступный фокус. Рядом писать:

// Замечание: отсутствие стиля [page-tabs-disabled] — ui/data/remarks.json.

Единый источник замечаний — ui/data/remarks.json. В записи указывать ID, страницу, блок, селектор, конкретные недостающие состояния, базовое оформление и исходный файл. В SCSS хранить только ссылку по ID, а не вторую копию описания. HTML и команда pnpm remarks:md используют JSON; номера строк вычисляются по ссылке в коде. Markdown — генерируемое представление, вручную не редактировать. Функциональный fallback не выдавать за дизайн.
После исправления или согласования состояния удалять запись JSON и ссылку по ID из исходника, затем обновлять Markdown. Согласованный акцентный цвет для отсутствующего hover считается решением: сохранять его как обычное правило без пометки об открытом замечании. В UI-каталоге оставлять только нерешённые замечания.

Transition задавать в базовом селекторе для реально меняющихся свойств, например color .2s ease, background-color .2s ease. Без transition:all. Учитывать prefers-reduced-motion; transition не оправдывает выдуманный эффект.

## Форматирование

Prettier: отступ 2 пробела, LF, ширина строки 100 символов; конфигурация — .prettierrc.json. Не сжимать авторские SCSS/CSS вручную: отдельные декларации, читаемые вложенность и блоки. Для новой или изменяемой страницы форматировать исходные стили и оставлять читаемым её итоговый CSS после сборки. Не форматировать ресурсы других страниц попутно. Проверки: pnpm format:styles:check и pnpm build. Для новой страницы расширить явные списки файлов команд format:styles, format:styles:check и format:css:build.

- Непрозрачные цвета записывать в HEX, включая токены и остановки градиентов: #0b2d4e вместо rgb(11, 45, 78) или rgba(11, 45, 78, 1). rgb()/rgba() использовать только для необходимой прозрачности. currentColor, transparent и наследование сохранять по назначению.
- Пиксельные размеры, отступы, координаты, рамки и тени округлять до целых: 1098.551px → 1099px, 1.687px → 2px. Не переносить длинные дробные хвосты из Figma в SCSS. Для пропорций использовать понятные проценты или простые отношения, а не вычисленную интерполяцию с множеством знаков.
- Округление относится к реализации, точные исходные значения остаются в кэше Figma. Сохранять композицию, пропорции изображений, выравнивание и подтверждённые переносы. При проверке учитывать округление отдельных размеров и возникающий суммарный сдвиг; не возвращать дробные значения или сложные формулы ради субпиксельного совпадения. Если округление вызывает видимое расхождение, исправлять раскладку и проверять соседние ширины.
- Для letter-spacing допустимы осмысленные значения в em из макета (например 0.04em), для line-height — простой безразмерный коэффициент. Их не округлять до целого числа em и не заменять вычисляемой интерполяцией.

## Прокрутка

- Вкладки: overflow-x:auto, скрытая полоса, touch/trackpad/клавиатура. При переполнении — grab/grabbing и drag-to-scroll через scrollLeft; после drag подавлять случайный click.
- Textarea и длинные списки: ограниченная высота, overflow-y:auto, тонкая полоса. Ползунок var(---Accent-Accent-100, #00AEEF), scrollbar-color/width и ::-webkit-scrollbar-thumb. Общие правила — миксин.
- Input сохраняет нативное перемещение длинного значения, без фиктивного вертикального scrollbar.
- Активный пункт/вкладка прокручивается внутри контейнера, без ненужного перемещения страницы.

После изменений: сборка, визуальная сверка локальных эталонов и функциональная проверка состояний.

## Типографика, сокращения и тени

- Типографику не придумывать: семейство, начертание, размер, line-height, letter-spacing, регистр и переносы брать из макета, требований или подтверждённого компонента. Если данных не хватает, сообщить в чате блок и недостающий параметр; до уточнения сохранить подтверждённый стиль или наследование и назвать это временным решением.
- По умолчанию писать свойства отдельно. font, background, mask и -webkit-mask всегда раскрывать. Другие сокращения допускаются только при очевидной необходимости, когда все значения заданы намеренно и нет нежелательных сбросов; нетривиальное исключение объяснить русским комментарием. font: inherit тоже раскрывать с сохранением наследования.
- Переносы сверять с эталонами. Использовать br с классами видимости по аналогии с главной: br, br-390, br-1440, br-above-1440, br-hide-390. На промежуточных ширинах предпочитать естественный перенос; классы вводить только для подтверждённого переноса, не для подгонки неизвестного макета.
- Тени задавать отдельными свойствами по макету: box-shadow для прямоугольного блока, filter: drop-shadow для прозрачного контура. Не запекать тень в PNG/SVG; исключать дублирование и обрезание. Если исходник уже содержит тень, проверить чистый экспорт или точное отделение внешней тени без изменения содержимого.
- При обнаружении расхождения с макетом сразу сообщить в чате блок, отличие и способ исправления или недостающие данные. Нерешённое отличие внести в реестр замечаний; исправленное удалить.
