# Структура и обслуживание проекта

## Страница и ресурсы

Vite + pnpm. Главная — index.html, остальные страницы — <page>/index.html.
Ресурсы страницы: src/scss/<page>/, src/js/<page>/, public/<page>/assets/.
Стили, шрифты, изображения и авторский JS независимы от других страниц.
HTML, PHP и данные сборка не генерирует.

- SCSS: _vars.scss, _mixins.scss, _fonts.scss, reset.scss, blocks/, вход style.scss.
- Изображения: public/<page>/assets/img/<block>/; шрифты — assets/fonts/. В исходниках пути абсолютные: /<page>/assets/....
- Готовые блоки, включая header/footer, копировать в новую страницу и менять только копии. Правила подключения скриптов — в навыке [javascript](skills/javascript/SKILL.md).

## Команды

Все команды ниже выполняются внутри layout-safu/.

| Команда | Назначение |
| --- | --- |
| `pnpm build` | Проверка данных, обновление Markdown замечаний, Vite и форматирование итогового CSS |
| `pnpm preview` | Предпросмотр собранной вёрстки для браузерной проверки |
| `pnpm format:styles` | Форматирование явно перечисленных исходных SCSS и служебного CSS |
| `pnpm format:styles:check` | Проверка форматирования без исправления |
| `pnpm project:data:check` | Проверка реестров и путей компонентов |
| `pnpm check:project-data` | Тесты обработки проектных данных |
| `pnpm remarks:md` | Обновление Markdown из реестра замечаний |

- Корневые команды импорта отличаются от сборки вёрстки; см. [интеграцию в Битрикс](../../AGENTS.md#интеграция-в-битрикс).
- Конфигурацию и package.json менять только в необходимом объёме задачи.
- Prettier: 2 пробела, LF, 100 символов. При добавлении страницы расширять явные списки format:styles, format:styles:check и format:css:build. Не форматировать чужие страницы и не менять минификацию JS попутно.
- Сборку и preview выполнять по необходимости проверки интерфейса, а не запускать бессрочный pnpm dev для любой задачи.

## Реестры

Назначить одного владельца реестров на время параллельной работы. Исполнители передают ему сведения о своих изменениях.

- ui/data/pages.json — страницы служебного /ui/. После создания страницы добавить ссылку, макет, честный статус и замечания. Наличие HTML не означает успешную проверку.
- ui/data/remarks.json — единственный источник открытых замечаний: ID, страница, блок, селектор, состояния, применённое оформление и исходный файл. Для расхождения текста или геометрии допустим description при пустом states.
- В SCSS не хранить комментарии-маркеры. UI определяет строки по селектору. Markdown для страниц с remarksReport — генерируемое представление; вручную его не править.
- Исправленное или согласованное замечание удалить из JSON и обновить Markdown. В UI показывать только открытые замечания.
- ui/data/blocks.json — самостоятельные БЭМ-компоненты. Ключ entries — страница + ID блока; new и existing (перенос/адаптация) учитывать отдельно. Экземпляры, элементы, модификаторы, контейнеры и типографические классы новыми компонентами не считать.
- Для нового блока указывать страницу, дату YYYY-MM-DD по Asia/Tomsk, этап и ID задачи. Неподтверждённые исторические данные — null. В auditedPages добавлять страницу только после проверки полного списка; иначе статус «Нет данных».
- purpose/files/reuseSource описывают назначение, исходники и источник копирования. reusableComponents — подтверждённые примеры для переиспользования; в статистические счётчики они не входят.
- Перед новым блоком проверить каталог и исходники аналога, после изменения обновить сведения. Пути проверить через pnpm project:data:check.

## Статистика

Учёт журналов, токенов и этапов не запускать автоматически.
По отдельному запросу использовать [statistics.md](statistics.md); инструменты и служебный UI сохраняются.
Сырые журналы, переписка, команды, секреты и абсолютные пути журналов не должны попадать в репозиторий.
